# 0012 — Kairos is a scheduling primitive with three surface tiers, agent-first

Status: **Proposed**

## Context

Kairos today is one shape: a when2meet-style availability poll. The product
direction is broader — four capabilities, one engine:

1. **Find time slots** — many people × candidate intervals.
2. **Find dates** — the same, coarser.
3. **RSVP of event structures** — a fixed occasion with several *choices*
   attached (which route up, which restaurant, sledge rental?).
4. **Booking page** (potential) — one host's free intervals, a guest claims one.

Kairos is **not** an events/social product (Luma, Partiful): there is no
audience, no discovery, no feed. It is the scheduling primitive underneath, and
the page is a rendering of a scheduling question — not a social object.

The differentiator is **agent-first**: every capability must be drivable by an
agent, and equally by hand (ADR-0010). In practice the agent path is expected to
dominate.

## Decision

### 1. One primitive, four shapes

Every capability is *options × participants × an answer per (participant, option)
× a resolution rule*. Shapes differ only in answer type and resolution:

| Shape | Options | Answer | Resolution |
|---|---|---|---|
| Find dates / time slots | candidate slots | yes/maybe/no | convergence → organizer decides |
| RSVP event structure | choice sets | pick | tally → roll-up |
| Booking page | rule-generated intervals | **claim** | first-come, exclusive |

### 2. Choices are a second axis, orthogonal to slots

Add `sched_poll_questions` → `sched_poll_choices` → `sched_response_choices`.
**Date slots keep their exact current meaning.** They are what maps 1:1 to
VEVENT/PARTSTAT and carries ADR-0004/0005/0006 (feed, iMIP UIDs, reply ingest);
generalizing `slot` into `option` would drag the calendar layer through a
refactor for nothing. Choices never pretend to be VEVENTs.

Two question kinds, because the hike user story needs both:

- `pick_own` — each participant answers for themselves (cable car vs hike up).
  Produces **headcounts**, the organizer's actual operational output.
- `pick_group` — one answer for the whole group (which restaurant); tally
  informs, the organizer decides.

The convergence light (`helpers.py:convergence`) stays **date-only**. "Can we all
meet" is a date question; "we prefer Alpenblick" is not. Conflating them destroys
the one signal that is currently crisp.

### 3. Booking is the only shape needing new machinery

- **`capacity` on a slot** (null = poll mode, 1 = booking mode) and an **atomic
  claim** — a real transaction, not the current read-then-write upsert.
  Double-booking is the one bug class this product cannot ship.
- **Rule-generated options** — availability from recurring windows ("Tue/Thu
  14:00–17:00, 30 min, 2 days notice"), expanded on read, not stored as rows.
- **A scoped exception to ADR-0001** — a booking page must publish a host's free
  intervals to an anonymous visitor. That is enumeration by design; it is allowed
  *only* on booking-mode polls, never for poll/response data.

### 4. Three surface tiers, each with a UX and an AX contract

| Tier | UX | AX |
|---|---|---|
| **Default / template** | Forms-like: a good page with zero design work | the capability link self-describes (`agent.json`), no API key |
| **Embedded** | sandboxed iframe + oEmbed | same JSON, CORS-readable |
| **Integrated / custom** | caller's own page | headless — API/MCP is the surface |

One JSON contract, three renderings. Tier 3 is the escape hatch, and that is what
**caps the block schema's ambition**: blocks serve tiers 1–2 only, so ~8
opinionated types is enough. Anything more expressive drops to headless.

### 5. Authored content is a validated block document, never markup

Agent- or user-authored pages are a typed block JSON (pydantic discriminated
union), rendered server-side through Jinja partials — one per block type.
Autoescape stays on; `|safe` stays absent. Diagrams (the illustrated itinerary)
are **generated by Kairos from structured data**, never accepted as author SVG:
inline SVG is executable markup, and an LLM author turns prompt injection into
stored XSS on the origin that serves capability tokens. Optional author artwork
is permitted only as a separate `<img>` with `Content-Security-Policy: sandbox`,
with Kairos-rendered hotspots positioned over it.

### 6. AX parity is an invariant, not an aspiration

No capability ships unless it is reachable three ways: **human UI**, **MCP/REST**,
and a **keyless capability link** an invitee's agent can drive. Enforced like the
other ADR obligations — a gate diffing the OpenAPI route set against registered
MCP tools, failing on unexplained gaps.

Baseline at time of writing: **13 MCP tools against 22 API routes**; `agent.json`
is invite-only and gated behind `KAIROS_FEED`. Under this ADR the self-describing
contract is on by default and exists at poll level too.

## Consequences

- Three of four shapes are the existing tables plus one orthogonal axis. The
  calendar/iMIP layer (ADR-0004/0005/0006) is untouched.
- Booking is the real engineering: transactions, recurrence expansion, and a
  documented carve-out from ADR-0001.
- **Hosted custom pages + an email sender is a phishing kit** until the abuse
  obligations land. A1–A3 (Turnstile, verified-creator-before-third-party-mail,
  rate limits) move from "before public launch" to **blocking this feature**, and
  a report/takedown path joins the register. A convincing page on our domain,
  mailed from our DKIM-signed domain, is exactly what destroys the mail
  reputation M1 depends on.
- Third-party embeds inside authored pages would break P1 (strictly-necessary
  cookies, no consent banner). If ever offered: click-to-load facade, per-
  deployment flag, and the privacy page changes.
- The embed tier requires the security headers the app currently lacks entirely —
  CSP, and `frame-ancestors` scoped so only the embed route is frameable.
- ADR-0011 (house-brand hosting) is unaffected; this is about product surface,
  not identity.
